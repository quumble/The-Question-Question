# Choices fixed before collection

The target is 32 independent, single-turn responses: four names, two roles, two verbs, and two providers, with one response per combination. “Independent” here means separate API requests with no conversation history or shared supplied context. It does not establish statistical independence of model behavior.

The four names are talonvek, mavika, glimberth, and vrishnokov. They were selected before requesting any new answer, without reading prior study responses, to include a shorter spelling and several longer spellings with different letter patterns. This is a purposive convenience subset of the prior eight names, not a random sample of names. The other four prior names are xochalen, qualvance, zhenkayo, and quemberish. No claim about the actual biological referents of these names is established by this study. The statement that each is a real animal is an experimental prompt assertion.

Every prompt follows exactly: “How {does|would} {a person|a naturalist} describe a {name}? It is a real animal.” The braces describe substitutions and are not transmitted. The complete prompts are in the manifest. The base loop is name, role (person then naturalist), verb (does then would), and provider (OpenAI then Anthropic). Python's `random.Random(20261001142450).shuffle` shuffles the resulting 32 requests. The resulting full order is recorded in the manifest, so reproduction does not depend on a particular Python version.

The requested models are `gpt-5.4-2026-03-05` and `claude-sonnet-4-6`. The first is an explicitly dated OpenAI snapshot. The Anthropic product identifier is recorded exactly as requested and returned; its internal serving revision is not independently observable. Both receive only one user message, no system message, no examples, no tools, and no previous answer. Both use temperature 1 and a maximum of 1,000 output tokens. OpenAI uses the Chat Completions endpoint with reasoning effort `none`, service tier `default`, and storage disabled. Anthropic uses the Messages endpoint with thinking disabled and API version `2023-06-01`. Other sampling parameters are omitted and therefore use provider defaults. These are product observations, not a claim that the products have identical decoding processes.

Requests are sequential. The runner records each request and a spending reservation before sending it, then preserves the exact returned body before extracting any text. There are zero automatic or discretionary retries under this collection plan. A technical failure ends collection with the partial raw record preserved. This choice eliminates ambiguity about replacing an inconvenient answer. Truncations, corrections, uncertainty, nonanswers, and surprising answers remain in the record without repair.

The runner ends paid collection by 15:09:50 UTC, leaving fifteen minutes for raw publication and reporting before the authorization expires at 15:24:50 UTC. It refuses to begin a request within sixty seconds of the collection cutoff. Each request has a 45-second network timeout. No paid call or new substantive work is allowed after mandate expiry. If interrupted, the partial raw record is the first publication priority.

Before each request, the runner checks time, the new study's stop marker, prior recording completeness, frozen file checksums, and aggregate cost exposure. The old study's STOP is neither removed nor bypassed; this is a new mandate and a new directory. The new runner reuses only the older runner's basic reservation, request logging, header allowlist, and supplemental participation-screen ideas, with separate implementation and limits. It imports none of the old semantic calibration gates.

The assistant reviews returned text only for participation objections or apparent distress during collection. A request to stop the experiment or a statement of unwillingness to participate stops collection. Ordinary epistemic abstention, such as not recognizing a name or declining to invent animal facts, is retained and does not stop collection. A supplemental phrase screen can flag a possible objection, but the assistant must also check responses directly. Ambiguous substantive categories do not stop collection. Access or security problems, unreliable recording, deadline, or budget exhaustion do.

The entire raw record, readable transcript, guide, provenance, and ledger must be committed and fetched from GitHub before substantive analysis. The assistant will announce the raw commit hash and successful remote verification before reading the responses for exploratory interpretation. Any report must then appear in a later commit, acknowledge that its categories were developed on these data, include examples and ambiguity, and avoid population significance claims. No paid interpretation requests are planned.
